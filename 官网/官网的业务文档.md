# CoserOps 官网业务、产品与双语 SEO 规范

版本：v1.0 | 更新日期：2026-10-04 | 项目：coserops-website
正式域名：https://www.coser.eu.org

本文是官网重建的业务、内容、设计、开发与运营共同依据。官网从 CoserOps 的产品定位与客户需求出发重新规划，不继承现有 Astro Starter 的页面数量、导航或示例内容。本文描述建设要求，不代表相关产品能力已经上线。

## 1. 品牌与官网定位

### 1.1 固定品牌口径

| 项目 | 统一写法 |
| --- | --- |
| 对外品牌 | CoserOps |
| 品牌全称 | Coser Operations Center |
| 产品类别（英文） | Multi-channel Customer Operations Platform |
| 产品类别（中文） | 多渠道客户运营平台 |
| 英文口号 | One place to operate every customer channel. |
| 中文口号译文 | 在一个工作空间，开展每个客户渠道的运营。 |
| COSER 官方释义 | Customer Operations, Service, Engagement and Reach |
| COSER 中文含义 | 客户运营、服务、互动与触达 |

对外标题、Logo、导航、社交资料、结构化数据和销售材料统一使用 **CoserOps**，首次完整介绍可使用 “CoserOps (Coser Operations Center)”。不得仅使用 “Coser” 作为对外品牌；COSER 仅用于解释名称含义。品牌不是法律主体，不能以品牌名代替尚未确认的运营主体。

About 中固定使用以下英文句子，翻译不得改变官方释义：

> CoserOps stands for Coser Operations Center. COSER stands for Customer Operations, Service, Engagement and Reach.

对应中文：

> CoserOps 是 Coser Operations Center（客户运营中心）的品牌名称。COSER 代表 Customer Operations, Service, Engagement and Reach，即客户运营、服务、互动与触达。

口号表达产品方向，不代表所有渠道均已接入或可无限制使用。口号附近的产品说明必须引导访客查看真实能力状态。

### 1.2 官网与产品的边界

本项目建设的是 **CoserOps 客户运营中心平台的官方网站**，不是客户运营产品后台。官网提供产品解释、场景内容、渠道信息、品牌资料和咨询入口；客户记录、消息收发、坐席工作台、活动执行、权限和计费属于产品应用。

官网承担五项任务：

1. 让目标访客迅速理解产品类别、业务问题、产品方向与适用边界。
2. 获取具备明确客户运营需求的有效线索，并交给负责人跟进。
3. 用可核实的主体信息、能力状态和内容建立信任。
4. 成为 CoserOps 品牌、产品与渠道信息的权威公开来源。
5. 为未来的演示、试用、登录等产品入口预留位置。

唯一公开官网及规范地址为 `https://www.coser.eu.org`；站点地址、canonical、sitemap 和 robots.txt 均使用该地址。根域 `coser.eu.org` 暂不在本次范围内，不处理或配置，也不对其 DNS、重定向、canonical、sitemap 或 SEO 作任何假设，当前没有根域重定向计划。其他子域可按职责隔离产品应用、管理/控制后台、API、静态资源和预览环境；具体地址与开放范围按实际配置确认，不代表全部子域公开或可被索引。

产品应用未来可考虑部署于 `app.coser.eu.org`，但该地址、开放时间和注册方式尚未确定。未有真实可用入口前，不展示登录、立即试用、购买或已开放演示的按钮。

### 1.3 受众与转化目标

初始内容优先围绕有跨渠道客户沟通需求的运营负责人、客服负责人、增长团队与业务决策者组织。企业规模、行业和优先国家仍需确认；此处是内容定位假设，不能写成已有客户事实。

主要转化为“咨询客户运营方案 / Discuss your customer operations”。次要转化为阅读产品、场景与渠道状态。有效线索至少具备可回复联系方式、具体场景以及可判断的渠道需求；内部进一步依据服务地区、能力适配度与实施时间判断，不把所有点击计为客户。

## 2. 产品叙事与能力真实性

### 2.1 围绕客户生命周期组织产品

核心问题：潜在线索、触达记录、客服对话与社群互动分散在不同渠道，团队难以接续客户上下文。

产品方向：以统一客户记录连接渠道上下文，让团队围绕同一客户持续开展工作。统一记录应表达身份关联、来源、许可与偏好、互动历史、跟进状态等概念；跨渠道身份合并的实际规则必须经产品确认，不能承诺自动识别所有客户。

| 生命周期环节 | 访客关心的问题 | 官网应解释的产品方向 | 必须确认的能力边界 |
| --- | --- | --- | --- |
| 发现与获取线索 | 如何承接有意向的客户？ | 线索来源、授权获取、客户记录与归属 | 来源接入、导入方式、去重与分配是否实现 |
| 触达与活动 | 如何向合适的客户发送相关信息？ | 按客户背景开展经许可的触达与活动 | 授权、分群、调度、模板、限额与退订机制 |
| 客户支持与收件箱 | 如何让团队接续服务？ | 会话上下文、收件箱、协作与跟进 | 已接入的消息类型、坐席、分配与同步范围 |
| 关系与社群互动 | 如何持续维护客户关系？ | 联系人互动、社群关系与后续跟进 | 群组或社群能力、权限与平台限制 |

统一客户记录与渠道上下文是贯穿四个环节的产品主线，不能将官网写成互不相关的群发工具列表。上述内容是产品范围描述；每个具体功能都必须通过状态登记后才可对外表述为可用。

### 2.3 内容注册表：唯一事实来源

在内容层建立注册表，页面、能力徽标、渠道卡片与结构化数据引用同一份记录。业务与产品负责人负责事实确认；编辑不能独立把状态改成 Current。

| 字段 | 内容要求 |
| --- | --- |
| `id` / `type` | 稳定标识；品牌、功能、渠道、场景、案例或联系方式 |
| `locale` / `translationKey` | 语言及跨语言页面对应关系 |
| `name` / `summary` | 本地化名称和经审核的公开描述 |
| `status` | Current、In development 或 Planned |
| `availability` | 适用地区、开放对象、版本、权限、平台前提与限制 |
| `evidence` | 验收记录或可核实来源；内部证据不得直接公开 |
| `owner` / `verifiedAt` | 事实负责人和最近核实日期 |
| `publishState` | draft、review 或 published；与产品能力状态分别管理 |
| `seo` / `route` | 本地化标题、描述、路径、索引策略与对应页面 |

状态使用规则：

- **Current / 当前可用**：已有验证证据，且可对明确对象提供；受邀测试需注明，不能写成所有人可用。
- **In development / 开发中**：负责人确认正在开发；说明方向与限制，不承诺完成日期，不提供不可用的试用入口。
- **Planned / 规划中**：已确认的规划方向，不代表已启动开发或必然交付。
- **尚未核实**属于内部审核状态，不是公开能力状态。未核实条目留在草稿，不擅自归为 Planned。

当前文档不能确认任何具体渠道或功能已可用。Phase 0 必须完成逐项核实；若仍无法确认，可以发布介绍产品方向的官网，但不发布“已支持渠道”列表。渠道页只有在状态与实质内容经审核后才公开索引。没有案例授权时，使用明确标注的“场景示例”，不创建虚假客户故事或指标。

## 3. 双语信息架构与 URL 规范

### 3.1 语言策略

第一版同时建设简体中文和英文，分别采用 `/zh-cn/` 与 `/en/`。选择 `zh-cn` 是为了明确当前简体中文版本的范围，并为以后其他中文区域版本留出空间；它不表示业务仅面向中国大陆。若实际受众要求通用简体中文或繁体中文，应在 Phase 0 确认后一次性调整语言策略，避免发布后反复迁移。

- HTML `lang` 使用 `zh-CN`、`en`；`hreflang` 使用 `zh-CN`、`en`。
- 每个 URL 只承载一种语言的主体内容、导航、表单、SEO 元信息和错误提示；品牌、渠道名与固定释义可以保留专名原文。
- 根路径 `/` 使用 HTTP 302 跳转到固定的中文首页 `/zh-cn/`，不再显示语言选择页。用户通过导航切换语言，不依 IP 或浏览器语言决定跳转目标。
- 首页语言组的 `x-default` 指向中文首页；根路径不收录到 sitemap，不生成重复首页正文。

### 3.2 路由与页面目的

以下为两种语言的页面模板；动态页面只有具备独立价值时发布，不因存在模板就生成空页面。

| 页面 | 中文 URL | 英文 URL | 目的与主要 CTA |
| --- | --- | --- | --- |
| 首页 | `/zh-cn/` | `/en/` | 解释定位与价值；咨询、了解产品 |
| 产品 | `/zh-cn/product/` | `/en/product/` | 生命周期、统一记录、能力状态与边界；讨论适配性 |
| 解决方案总览 | `/zh-cn/solutions/` | `/en/solutions/` | 按客户问题选择场景；进入具体方案 |

| 博客文章 | `/zh-cn/blog/{slug}/` | `/en/blog/{slug}/` | 回答一个具体搜索问题；关联产品或方案 |
| 联系 | `/zh-cn/contact/` | `/en/contact/` | 收集需求或直接沟通；提交咨询 |

渠道标识采用 `telegram`、`whatsapp`、`sms`、`email`。首批解决方案建议围绕线索承接、经许可的触达、客户支持和社群互动编排，具体发布数量由事实与内容完整度决定。

静态路径使用统一的 ASCII 英文短词，降低维护和复制成本；正文与 SEO 文案必须本地化。文章 slug 可按语言单独编辑，例如英文 `consent-based-outreach` 对应中文 `kehu-chuda-shouquan`，通过 `translationKey` 映射，不靠替换 URL 前缀猜测译文。发布后保持 slug 稳定；修改时建立一跳永久重定向。

主导航：产品、解决方案、渠道、资源、关于、联系，以及语言切换。页脚补充品牌全称、经确认的联系方式和法律页面。移动端保持相同信息层级。

### 3.3 多语言索引要求

1. 每个可索引页面使用自身完整 HTTPS URL 作为 canonical。中文页面不 canonical 到英文；根路径仅返回重定向，不输出 canonical 页面。
2. 已发布的中英文对应页面输出互相回指、包含自身的 `hreflang`，目标必须是 HTTP 200、可索引且 canonical 一致的页面。
3. 首页语言组的 `x-default` 指向中文首页 `/zh-cn/`；其他可索引页面的 `x-default` 指向同一主题的英文页面，避免全部指向无关首页。
4. 译文尚未发布时不输出不存在的替代语言链接，不把不同主题页面配成一组；语言切换应说明该页暂无译文，并提供明确标注的目标语言首页入口。
5. 语言切换默认保留当前页面意图，不一律返回首页。使用可抓取的 `<a>` 链接，不仅依赖客户端脚本。
6. `/sitemap.xml` 作为 sitemap index，引用 `/sitemap-zh-cn.xml` 和 `/sitemap-en.xml`；根路径仅重定向，不加入索引。只收录 `www.coser.eu.org` 上 HTTP 200、可索引的 canonical 页面 URL，其他子域不进入官网 sitemap，`lastmod` 反映真实内容更新。
7. `robots.txt` 允许抓取公开内容并指向 sitemap index。不要用 robots 屏蔽代替移除索引；需要 `noindex` 的页面须允许爬虫读取该指令。
8. 除非明确决定公开并允许索引，其他子域须设置 `noindex`；私有应用和管理后台另需访问控制。预览环境优先访问控制，并设置 `X-Robots-Tag: noindex`；草稿不生成公开路由。站内搜索、薄弱标签页、提交成功页等设 `noindex` 且不进入 sitemap；API 不作为页面索引。
9. 不存在的 URL 返回真实 HTTP 404，并按路径语言显示导航与返回入口，不能回写首页 HTTP 200。下线且无替代内容可返回 410，有等价替代时才永久重定向。

### 3.4 URL 治理

统一 HTTPS、正式主机 `www.coser.eu.org`、小写路径和尾部斜杠。仅对已配置和控制的别名域做 301/308 到正式域；根域 `coser.eu.org` 不在此策略范围内，暂不处理。避免重定向链。旧模板 URL 逐项判断是否有等价内容，没有则返回 404/410，不批量跳首页。大小写与斜杠变体归一；UTM 等跟踪参数不进入 canonical 或 sitemap，不能因参数产生可索引副本。普通语言切换不用永久重定向表达用户语言偏好。

### 4.2 产品、解决方案与渠道页面

**产品页**回答“这是什么、为何需要、如何组织工作、现在能用什么”。包含生命周期流程、统一记录概念、能力状态表、适用条件、限制和咨询入口。功能示意与真实截图严格区分。

**方案页**回答一个业务问题。使用“目标团队 → 当前流程与痛点 → 建议工作流程 → 涉及能力及状态 → 使用前提 → 相关渠道与资源 → 场景咨询”的结构。描述可观察的改进目标，不保证增长、收入或效率百分比。

**渠道页**分别解释 Telegram、WhatsApp、SMS 与 Email 的业务用途、CoserOps 接入状态、授权与账号前提、地区或供应商限制、支持及不支持的操作、核实日期和相关方案。明确区分“平台本身提供的能力”与“CoserOps 已集成的能力”。开发中或规划中页面如有实质信息可以索引；只有名称与占位文字时保持草稿。

### 4.4 资源、联系与法律页

- 资源中心按客户生命周期和渠道组织指南，不以发布时间作为唯一分类；首批可从“多渠道客户运营是什么”“如何规划客户上下文”“客户触达的授权与退订”“渠道选择与支持流程”中选择有专业审核能力的主题。

### 5.2 页面级 SEO

- 每页一个明确 H1，标题层级按内容组织；Title、H1 与正文共享同一意图，但无需机械重复。
- Title 使用“主题或价值 + CoserOps”，避免关键词罗列；英文约 50–60 字符、中文约 25–35 字可作为预览起点，不是 Google 硬性限制。
- Meta description 说明页面内容与下一步，不承诺结果；英文约 140–160 字符、中文约 70–90 字作为编辑参考，最终以实际展示宽度和清晰度为准。
- 每种语言独立撰写自然文案、例子与行动说明，事实和状态保持同步。机器翻译只能作为草稿，不能发布无人审核的薄内容；不要为凑字数重复段落。
- 产品页链接方案和渠道；方案页链接对应能力、渠道与指南；文章链接一项相关方案或产品及延伸阅读；联系入口全站可达。锚文本描述目标内容，避免批量“点击这里”。
- 为信息型图片编写本地化 alt，装饰图使用空 alt。不要把关键词塞入 alt；图表的核心信息也用文字表达。
- OG/Twitter 配置本地化标题、摘要、绝对图片 URL 与图片说明；OG locale 使用 `zh_CN`、`en`，英文地区若需具体化应先确认。没有官方社交账号时不编造 Twitter handle。

### 5.3 结构化数据

JSON-LD 与可见内容和事实注册表一致，使用稳定的 `@id` 关联实体。

| 类型 | 应用条件 |
| --- | --- |
| Organization | 确认运营组织身份后使用；区分品牌与法律名称，`sameAs` 仅列真实官方账号，不虚构地址或资质 |
| WebSite | 描述正式网站、品牌名称、URL 与语言；没有站内搜索不添加虚假的 SearchAction |
| SoftwareApplication | 产品信息足够真实完整时用于产品页；开发状态清晰，不虚构价格、评分、下载或可用系统 |
| BreadcrumbList | 与页面可见层级一致，用于方案、渠道和文章等内页 |
| Article / BlogPosting | 用于真实文章，作者、日期、图片与正文一致 |

富媒体结果展示不作保证。不添加虚假 Review、AggregateRating、Offer 或仅为搜索展示而编造的实体。

### 5.4 技术体验与发现

- 重要正文、链接与 SEO 标记直接存在于返回的 HTML；静态优先，不要求搜索引擎执行脚本才能理解产品。
- 使用 HTTPS，校验移动端导航、表单、文字可读性与无障碍。支持键盘、焦点可见、足够对比度、表单标签和减少动态效果。
- Core Web Vitals 目标：真实用户第 75 百分位 LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1。上线前用实验室测量发现问题，上线后有足够样本再用真实数据判断，不把实验室评分等同于排名保证。
- 图片生成合适尺寸与现代格式并预留宽高；首屏关键图避免懒加载，非首屏按需加载；控制字体、第三方脚本与客户端 JavaScript。
- 在 Google Search Console 验证 Domain property，提交 sitemap index，检查两种语言代表页面的抓取、索引和 Google 选择的 canonical；部署记录保留 sitemap 提交与索引问题处理责任人。
- Google 为主要搜索渠道；Bing Webmaster Tools 可在主流程稳定后补充。内容质量、竞争与地区会影响结果，不承诺排名、收录时间或自然流量。

## 6. 线索转化与跟进流程

### 6.1 CTA 与联系路径

默认主 CTA 为“咨询客户运营方案 / Discuss your customer operations”。页面携带相关产品、方案或渠道上下文进入联系页。只有演示已可交付且有人承接时才使用“预约演示”；试用同理。

路径：搜索或分享 → 对应语言落地页 → 产品/场景与状态 → 咨询表单或 Telegram/WhatsApp/Email → 接收确认 → 负责人判断与跟进 → 记录结果。

Telegram 用户名或机器人地址、WhatsApp Business 号码或链接、联系邮箱均须确认所有权、可用性与接收人。不得编造账号或发布占位链接；外部渠道点击仅说明“准备联系”，不等于消息已发送。

### 6.2 表单字段与同意

| 字段 | 规则 | 目的 |
| --- | --- | --- |
| 姓名/称呼 | 可选 | 称呼与沟通 |
| 公司/组织 | 可选 | 判断业务背景 |
| 回复方式与地址 | 至少一种可用联系方式；按类型校验 | 回复咨询 |
| 关注渠道 | 多选，可选 | Telegram、WhatsApp、SMS、Email 或其他 |
| 需求描述 | 必填并限制长度 | 理解流程、问题与适配性 |
| 团队规模、主要地区、计划时间 | 可选，优先简短选项 | 辅助资格判断，不强迫提供预算 |
| 隐私告知与必要同意 | 按适用处理依据设置，不预勾选 | 解释处理目的与隐私政策 |
| 营销订阅同意 | 如启用则独立、可选、不预勾选 | 与咨询回复分开，不捆绑 |

不要求身份证明、客户通讯录或敏感业务附件。首次来源、落地页、语言、相关内容 ID 和允许的 UTM 字段可作归因；仅保存必要的白名单字段并限制长度，避免保存包含个人信息的完整 URL。跨访问追踪遵循同意要求。

### 6.3 接收与异常处理

- 前后端校验、输入长度限制、频率限制、蜜罐或按需 Cloudflare Turnstile、防重复提交随表单同时交付；密钥仅保存在服务端，表单日志脱敏。
- 提交中提供可访问状态；只有服务端确认已持久接收或交给可靠队列后才显示成功，单纯按钮点击不计转化。
- 失败保留输入、说明可重试原因并提供已核实的替代联系方式；不能因统计脚本失败影响咨询。
- 首版可将咨询送到指定团队收件箱或 CRM，明确负责人、通知失败告警、重复线索处理、跟进状态和保留期限。未接好后端时先使用真实直接联系入口，不能上线假表单。
- 成功提示说明已接收与下一步；没有已批准的服务承诺时不写“24 小时内回复”。内部设跟进目标并按实际能力维护。

## 7. 技术架构与仓库重建范围

### 7.1 推荐架构

采用 Astro 静态优先官网方案，可继续使用现有技术栈，但围绕本规范重建内容结构。展示内容预渲染；语言切换、导航等尽量用原生 HTML；表单等确需服务端能力的部分通过 Cloudflare Workers 或经审核的服务实现。

内容初期使用 Astro Content Collections 或等价的结构化 Markdown/MDX 与配置管理，校验语言、页面对应关系、状态、SEO 和发布字段。编辑协作频繁时再引入 CMS，仍保留同一事实注册表与审核要求。不要把双语正文散落在组件条件判断里。

部署到 Cloudflare，使用与选定静态输出/服务端模式匹配的部署配置。建立正式与预览环境、环境变量、域名和缓存策略；预览访问控制独立于正式站。产品应用单独部署、独立权限与数据边界；官网不保存产品会话或客户业务数据。

## 8. 翻译、编辑与度量运营

### 8.1 双语生产流程

产品负责人确认事实 → 编辑建立页面 brief（意图、受众、主 CTA、关联事实）→ 撰写主稿 → 另一语言本地化 → 语言审核 → 产品与合规审核 → 技术预览 → 同步发布与登记核实日期。

核心页面要求双语齐备后上线；后续文章可单语先发，但不得生成空译文或虚假的 hreflang。事实变更时同时更新两种语言；无法及时更新的旧内容应撤回过期能力描述或暂时下线，而不是继续呈现冲突状态。

| 术语 | 中文统一用法 | 英文统一用法 |
| --- | --- | --- |
| 品牌 | CoserOps | CoserOps |
| 类别 | 多渠道客户运营平台 | Multi-channel Customer Operations Platform |
| 核心记录 | 统一客户记录 | unified customer record |
| 沟通背景 | 渠道上下文 | channel context |

| 关系 | 客户与社群互动 | customer and community engagement |

每月复核公开功能与渠道状态；发生功能、平台政策或联系方式变更时立即更新。每季度复核重点文章、内链、失效链接与翻译一致性。选题来源优先实际咨询问题、搜索查询与产品知识，发布频率服从审核能力，不以篇数代替价值。

### 8.2 衡量框架

| 维度 | 指标 | 解释与责任 |
| --- | --- | --- |
| Google 搜索发现 | 两种语言的索引状态、曝光、点击、CTR、查询主题 | SEO 负责人按落地页和语言观察；平均排名仅作诊断 |
| 内容参与 | 产品/方案阅读、相关内容点击、CTA 点击 | 区分内容作用，避免把点击当销售结果 |
| 咨询转化 | 表单开始、服务端确认接收、直接联系点击 | 外部消息是否发送需后续确认 |
| 线索质量 | 有效线索数、适配渠道/场景、后续沟通结果 | 业务负责人在 CRM 或受控记录中维护 |
| 服务与体验 | 跟进时效、提交失败率、CWV、失效链接 | 开发与业务共同处理 |

可使用 GA4 或经评估的替代统计方案。按适用地区要求，在取得必要同意前不启用非必要追踪；拒绝统计不影响浏览与咨询。事件仅携带语言、页面类型、内容 ID、CTA 和渠道等非敏感字段，不发送姓名、邮箱、电话号码或需求正文；限制日志与统计访问权限。

建议事件：`cta_click`、`contact_channel_click`、`lead_form_start`、`lead_submit_success`、`lead_submit_error`。成功事件对应可靠接收结果并去重；内部线索状态不直接回传包含个人信息的数据。结合 Search Console 与业务跟进观察归因，说明同意限制和跨设备导致的数据缺口。上线后先建立 4–8 周基线，再确定季度内容和转化目标，不预设没有依据的增长数字。

## 9. 合规与公开承诺边界

- 消息触达遵守适用法律、用户许可、退订要求与 Telegram、WhatsApp、SMS 服务商、邮件平台等实际条款。不得宣传抓取个人信息、绕过平台限制、无限发送、封号规避或未经许可的营销。
- 接入方式、配额、地区和模板审批等限制由实际供应商与产品实现决定；营销文案必须披露会影响客户决策的前提。
- 不承诺保证送达、保证转化、绝对安全或未经证实的合规认证。不因托管于 Cloudflare 或域名后缀而声称满足某地区全部监管要求。
- 公司主体、目标地区、数据流向和供应商明确后，再确定隐私、Cookie、跨境、备案及行业要求。官网咨询许可不自动等于产品客户消息的营销许可。
- 客户 Logo、评价、截图、字体、图片与案例都需事实和授权记录。公开文件不能泄露内部客户数据、账号凭据或未授权资料。

| Phase 2：内容与可信依据 | 按搜索意图发布指南、补充渠道深度内容、获授权案例和真实外部引用；持续改进内链与本地化 | 根据 Search Console 和咨询质量调整，内容有审核与维护负责人；不购买垃圾链接 |
| Phase 3：产品转化与集成 | 在产品真实开放后增加演示/试用/登录入口、CRM 集成和必要转化流程 | 实际产品可用，入口和权限清晰，官网与应用边界、法律协议和数据流程已确认 |

若首版内容量不足，减少方案/文章数量，不降低双语核心页面与事实准确性的要求。尚未具备资源内容时，资源入口延后公开而不是上线空栏目。

## 11. 上线验收清单

以下用于后续实施验收；本次文档重写不执行构建或测试。

### 品牌、内容与业务

- [ ] 全站使用 CoserOps，类别、全称、口号与 COSER 释义准确，About 固定句一致。
- [ ] 首页明确是多渠道客户运营平台官方网站，围绕客户生命周期和统一客户记录解释产品。
- [ ] 每项功能与渠道有可核实状态、负责人及使用边界；无虚构案例、数字、认证、合作或承诺。
- [ ] 双语核心页面可独立阅读；无模板示例、占位链接、空栏目或同一 URL 混合两套正文。
- [ ] 主体、版权、素材授权和法律披露已按实际情况确认。

### 多语言与 Google SEO

- [ ] `/` 返回 HTTP 302 到 `/zh-cn/`，中英文首页正常工作，HTML lang 正确；切换保留主题或明确提示无译文。
- [ ] 每页 Title、description、H1、OG/Twitter 与正文一致且本地化；图片 alt 合理。
- [ ] 对应语言页面自指 canonical，hreflang 双向、自引用且只指向真实可索引页面；x-default 按页面组设置。
- [ ] sitemap index 和语言 sitemap 只收录应索引 URL，robots 指向索引且不阻断需要读取 noindex 的页面。
- [ ] 预览受保护；草稿、成功页、薄弱分类等不进入索引；不存在的页面返回真实 404。
- [ ] HTTPS、域名、大小写、斜杠和旧 URL 策略一致，无重定向链或全站跳首页。
- [ ] 结构化数据符合可见事实，没有虚假评价、价格或不存在的功能。
- [ ] Google Search Console 已验证、提交 sitemap，并检查两种语言的代表页；不把待收录误报为已收录。

### 转化、体验与运营

- [ ] Telegram、WhatsApp、Email 等实际联系方式与接收负责人已验证。
- [ ] 表单如启用，校验、防垃圾、防重复、可靠接收、成功/失败提示和通知异常流程均已验证。
- [ ] 隐私告知、独立营销同意、必要统计同意和保留/删除规则与实际实现一致。
- [ ] 手机、桌面和键盘均可完成关键路径；字体、图片和脚本满足体验预算并留有测量记录。
- [ ] 事件区分点击、提交与有效线索，不发送个人信息；统计拒绝不影响咨询。
- [ ] Cloudflare 正式/预览环境、域名管理、权限、告警、回退与内容发布责任人已明确。
- [ ] 核心内容与能力状态有复核节奏，翻译、SEO、咨询跟进和异常处理均有人承接。

## 12. 待确认决策与默认处理

| 决策 | 需要确认的具体内容 | 未确认前的处理 |
