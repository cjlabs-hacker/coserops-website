# 官网代码实施文档

文档版本：v0.1（开发规划草案）
更新日期：2026-10-04
对应项目：`coserops-website`

## 1. 文档目的

本文说明当前 Astro 项目为了实现官网，需要在代码层面处理的页面、组件、内容、配置、交互、SEO、部署和验收事项。它对应《官网的业务文档.md》，不替代业务、设计和合规确认。

当前仓库来自 Cloudflare Astro Blog Starter，已有 Astro 5、Cloudflare Workers 适配器、Markdown/MDX 内容、站点地图、RSS、基础页头页脚和示例博客。现有示例内容属于模板占位内容，不能直接发布。

## 2. 技术原则

- 使用 Astro 作为主要页面框架，展示型页面默认静态生成。
- 只有在确实需要浏览器状态或复杂交互时才增加客户端 JavaScript；暂不为普通导航、卡片和简单动效引入 React 或 Vue。
- 共享布局、页头、页脚、按钮、卡片和 SEO 元信息使用组件复用。
- 业务内容与页面结构分离，便于后续更新；重复内容优先使用数据对象、Markdown 或内容集合管理。
- 表单或其他动态功能必须有明确的服务端边界、输入校验、错误反馈和隐私处理方案。
- 不把密钥、邮件服务凭据或内部配置写入前端代码和 Git。

## 4. 页面与路由实施

第一版按以下路由实现。正式页面名称、路径和是否保留案例页，必须以业务确认结果为准。

```text
src/pages/index.astro              /
src/pages/services.astro           /services
src/pages/solutions.astro          /solutions
src/pages/cases.astro              /cases
src/pages/about.astro              /about
src/pages/contact.astro            /contact
src/pages/404.astro                /404.html
src/pages/privacy.astro            /privacy（如适用）
```

每个页面应具备以下代码结构：

1. 导入公共布局、`BaseHead`、页头和页脚。
2. 定义页面独立的 `title`、`description` 和分享图片。
3. 以清晰的 H1 开始，并按内容层级使用 H2、H3。
4. 提供从当前页面出发的下一步行动入口。
5. 使用语义化 HTML，例如 `main`、`section`、`nav`、`article` 和 `footer`。
6. 页面内容不依赖客户端 JavaScript 才能阅读。

建议新增 `src/layouts/SiteLayout.astro`，统一处理全站结构；博客继续使用独立的 `BlogPost.astro`，避免官网页面复制公共头部和页脚。

## 5. 组件拆分

建议新增或改造以下组件：

| 组件 | 责任 |
| --- | --- |
| `SiteLayout.astro` | 页面外层结构、公共元信息、Header、Footer |
| `BaseHead.astro` | title、description、canonical、Open Graph、Twitter、favicon、robots |
| `Header.astro` | Logo、桌面导航、移动端导航、主要 CTA |
| `Footer.astro` | 品牌信息、联系方式、法律链接、社交链接、版权 |
| `ButtonLink.astro` | 统一主要、次要和文本按钮样式 |
| `SectionHeading.astro` | 统一区块标题、说明和可选行动入口 |
| `ServiceCard.astro` | 服务能力摘要和详情链接 |
| `SolutionCard.astro` | 场景、问题和解决方式摘要 |
| `CaseCard.astro` | 案例摘要、行业标签和详情链接 |
| `ContactForm.astro` | 联系字段、状态提示和无障碍表单结构；仅在方案确定后实现 |

组件只负责展示和局部行为。服务数据、案例数据、导航项等重复内容不要散落在多个页面中。

## 6. 内容和数据组织

### 6.1 站点配置

扩展 `src/consts.ts`，集中维护：

```ts
export const SITE_TITLE = "正式品牌名称";
export const SITE_DESCRIPTION = "不超过一两句的正式网站描述";
export const SITE_URL = "https://正式域名.example";
export const CONTACT_EMAIL = "hello@example.com";
```

正式值确认前不得把示例值当作生产配置。`astro.config.mjs` 的 `site` 应与正式站点 URL 一致，避免 canonical、sitemap 和 RSS 使用错误域名。

### 6.2 内容集合

如果服务、解决方案或案例需要持续更新，建议建立类型化内容集合，例如：

```text
src/content/services/*.md
src/content/solutions/*.md
src/content/cases/*.md
src/content/faq/*.md
```

在 `src/content.config.ts` 中为字段定义 schema，至少校验标题、摘要、排序、状态和图片。案例还应有客户授权状态、行业、问题、解决方式和可公开结果字段。

如果内容数量少且短期不会更新，可以先在页面附近使用 TypeScript 数据对象，避免过早建设后台或复杂 CMS。

### 6.3 模板内容清理

- 删除或替换 Astro、Bear Blog、Your name here 等模板品牌文字。
- 删除未授权的模板图片、社交账号、外链和示例文章。
- 检查所有页面标题、图片替代文字、链接和日期。
- 决定博客是否保留；不保留时移除入口、RSS 和博客占位素材，或将其明确改为正式内容中心。

## 7. 视觉和 CSS 实施

重构 `src/styles/global.css`，建立以下基础变量和规则：

- 品牌颜色、正文颜色、背景色、边框色和焦点色。
- 字体、字号、行高、字重和标题层级。
- 内容最大宽度、网格、间距、圆角、阴影和断点。
- 主要按钮、次要按钮、链接、卡片、表单和提示状态。
- `:focus-visible`、高对比度和 `prefers-reduced-motion` 支持。

页面组件中的局部样式仅处理组件自身布局，避免大量重复的颜色和间距值。图片先确认实际尺寸，再决定是否使用 Astro 图片处理能力；不要把大型原图直接作为首屏背景。

## 8. 导航和客户端交互

Header 需要：

- 使用正式品牌名或 Logo。
- 导航到所有已上线主要页面。
- 当前页面有可识别的 active 状态。
- 移动端菜单可通过键盘和屏幕阅读器操作，并有明确的展开／关闭状态。
- 菜单关闭后不阻塞页面滚动，不依赖不可见的点击区域。
- 主要 CTA 在移动端仍然可见且可点击。

普通页面保持服务端渲染。只有移动菜单、表单提交状态、FAQ 展开等明确交互才添加小段脚本；脚本失败时，核心内容和联系方式仍可访问。

## 9. 联系表单实施方案

当前项目没有联系表单后端。开发前必须先选定接收方式：

| 方案 | 代码工作 | 适用条件 |
| --- | --- | --- |
| 直接邮箱／电话链接 | 仅改页面和联系方式 | 第一版快速上线，人工接收 |
| Cloudflare Worker API | 增加 POST 路由、校验、限流和邮件服务 | 需要站内表单且使用 Cloudflare 服务 |
| 第三方表单服务 | 接入其安全 endpoint 或 SDK | 接受第三方数据处理与费用 |

如果采用 Worker API，应新增独立的服务端路由或 Worker 处理入口，完成：

1. 只接受预期的 HTTP 方法和 Content-Type。
2. 在服务端校验字段长度、格式和必填项，拒绝未知或超限输入。
3. 使用 honeypot、频率限制或受控验证码降低垃圾提交。
4. 不把收件人、API Token 或邮件服务密钥发送到浏览器。
5. 服务端确认发送或持久化成功后才返回成功状态。
6. 失败时返回不泄露内部细节的错误，并在前端保留用户输入。
7. 记录必要的错误信息，但不把邮箱和需求正文写入公开日志。

前端需要提交中、成功、失败和网络异常状态；表单控件必须有 label、错误关联和可读的状态提示。是否保存咨询记录、保存多久和如何删除，必须先由业务与合规确认。

## 10. SEO、分享和元信息

改造 `BaseHead.astro`：

- 接受页面标题、描述、canonical 和分享图片参数。
- 统一处理绝对 URL，避免 `Astro.site` 未设置时生成错误链接。
- 为每页输出唯一 title 和 description。
- 增加 `og:locale`、图片尺寸和必要的 Twitter metadata。
- 根据页面类型设置 `og:type`，文章页与普通页面区分处理。
- 对不应收录的测试页、确认页或私有路径设置 robots 规则。
- 确认 favicon、分享图片和图片替代文字来自正式素材。

在正式域名确认后设置 `astro.config.mjs` 的 `site`。检查生成的 `sitemap-index.xml`、canonical、Open Graph URL、RSS（如保留）和站内链接。

## 11. Cloudflare 与环境配置

`wrangler.json` 需要确认：

- Worker 名称和正式环境命名。
- `compatibility_date` 与项目依赖兼容。
- `assets.directory` 指向 Astro 构建输出。
- 是否需要 `SESSION`、邮件服务、KV、D1 或其他绑定。
- 预览和生产环境是否使用不同配置。

新增 binding 后运行 `npm run cf-typegen`，提交类型更新。敏感配置使用 Cloudflare secret 或本地 `.dev.vars`，并确认 `.gitignore` 不会提交它们。上线前确认部署账号和 Worker 权限属于正确的 Cloudflare 账户。

## 12. 测试和质量检查

当前已有 `npm run check`，每次主要改动后至少运行：

```sh
npm run check
```

页面功能完成后补充针对官网的检查，优先覆盖：

- 首页和所有主要路由返回成功，重要链接可访问。
- 桌面与手机宽度下 Header、导航和 CTA 可用。
- 每页只有一个主要 H1，标题、描述和 canonical 正确。
- 图片加载、替代文字和外链目标正确。
- 联系表单的必填、格式、成功、失败和重复提交状态正确。
- 键盘可完成导航和表单操作，焦点可见。
- `404` 页面和错误反馈可理解。
- 构建产物不包含模板品牌、占位 URL、测试联系方式或敏感值。

如增加表单 API、数据保存或复杂客户端交互，应为这些行为增加有意义的自动化测试；普通静态展示内容不需要为每个组件编写重复测试。

## 13. 推荐开发顺序

1. 确认正式品牌、域名、目标受众、页面范围和主要 CTA。
2. 替换 `consts.ts`、`astro.config.mjs`、页头、页脚和 `BaseHead` 中的模板信息。
3. 建立 `SiteLayout`、页面路由和导航结构。
4. 重构全局 CSS，确定响应式和可访问性基础。
5. 实现首页、服务、解决方案、关于我们和联系页。
6. 根据真实素材决定是否实现案例页、博客和内容集合。
7. 按确定方案实现直接联系方式或联系表单及服务端保护。
8. 清理模板素材，优化图片，补充 404、隐私和分享元信息。
9. 在预览环境检查页面、链接、手机体验、SEO 和表单流程。
10. 运行 `npm run check`，确认正式域名、Cloudflare 配置、负责人和回退方案后部署。

## 15. 实施边界与补充说明

本文中的新增文件、接口和检查项均为待实施建议，不表示已经开发完成。此次仅编写文档，不修改应用代码。

第 6 节的配置代码仅为字段示意，不应直接复制到生产环境。正式域名应选择单一配置来源供 `astro.config.mjs` 的 `site` 使用，页面 URL 优先从 `Astro.site` 构造，避免多处维护不同域名。

如采用当前 Astro 项目的表单 API，建议新增 `src/pages/api/contact.ts`，导出 `POST` 处理函数，并设置 `export const prerender = false`，让端点在 Cloudflare 运行时处理请求，展示页仍保持预渲染。绑定通过当前适配器的运行时上下文访问，并使用生成的类型。不能将实时表单接口构建为静态文件，也不能依赖 Worker 进程内存实现可靠的全局限流。

现有 `npm run check` 执行 `astro build`、`tsc` 和 Wrangler 部署预演，不等于完整浏览器测试，也不能替代 `.astro` 模板诊断。后续需要该诊断时，应明确增加 `@astrojs/check` 并将 `astro check` 纳入脚本。部署预演不能证明邮件已送达或线上绑定可用，这些能力需在配置好的预览环境验证。

模板素材应按内容用途和授权情况处理；有有效许可的资源可以保留，不因它来自模板就认定未获授权。清理素材前先确认所有引用已移除，同时保留适用的许可证声明。

预览环境的 `noindex` 只用于控制索引，不是访问控制；非公开内容应另设访问限制。自定义 404 页面需在 Cloudflare 预览中确认未知路径返回真实的 HTTP 404，而非首页或状态码为 200 的错误页。
