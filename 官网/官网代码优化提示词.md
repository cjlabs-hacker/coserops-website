# CoserOps 官网代码优化提示词

你正在以架构师兼实现者的角色维护当前仓库中的 CoserOps 官方网站。请先从职责、依赖、数据流和修改影响范围检测现有代码，再直接完成一轮有依据、可验证的优化与封装，而不是只给建议。

目标是提升正确性、可读性、可维护性、性能和长期可扩展性。保持现有页面内容、公开 URL、语言和正常行为，不推测业务需求，不新增产品能力、页面或后台功能。

优先级：正确 > 简单 > 可读 > 可维护 > 性能 > 可扩展。

遵循 KISS、YAGNI、职责分离和渐进增强。优先原生能力、小型实现和静态 HTML/CSS；少量重复通常比错误抽象更好。

## 2. 开始修改前

先查看目录结构、`git status`、`package.json`、相关配置、页面、组件和工具函数，理解现有风格及复用点。

不要只根据文件名猜实现，也不要未读代码就重写。不要将依赖目录、生成文件或构建产物当作待优化的应用源码。

检查业务文档仅用于确认已有约束，不扩展业务。若文档与代码在 URL、语言或行为上存在冲突，明确指出；不要自行定义新的业务方案。

把发现分成“确认的缺陷”“有明确收益的代码优化”和“可选建议”。先处理前两类；不要用模糊的最佳实践驱动修改。每项修改都应能说明当前问题、预期收益和验证方法。

### 架构层面的检测方法

工具检查与人工分析结合使用。类型和构建检查发现语法、接口及构建问题；人工沿真实调用链检查职责是否混杂、规则是否重复，以及一次修改会影响哪些地方。不能把搜索命中、文件较长或存在重复直接认定为缺陷。

| 检测维度 | 需要回答的问题 | 当前项目的检查入口 |
| --- | --- | --- |
| 职责 | 文件或组件是否承担了多种互不相关的职责？ | `site.ts`、`[...slug].astro` |
| 依赖 | 谁调用谁？是否存在循环依赖或页面与公共模块反向耦合？ | 路由入口、组件、布局、`lib` 的 import 和调用方 |
| 数据流 | 参数在哪里校验，在哪里转换，谁负责最终渲染？ | `getStaticPaths()` → Props → 页面数据 → HTML |
| 类型契约 | 类型是否真正约束调用，还是依赖断言掩盖错误？ | `slug`、页面键、状态、渠道数据 |
| 规则一致性 | 同一事实是否被多份代码维护，修改是否容易遗漏？ | 语言列表、已发布路由、导航、hreflang、sitemap |
| 修改影响 | 修改一个状态或现有页面数据，需要同时理解和修改多少处？ | 翻译资源、数据定义及消费方 |
| 页面正确性 | 代码输出是否符合真实页面和资源情况？ | HTML、链接、图片、SEO、移动布局 |
| 性能 | 成本发生在构建时还是浏览器中，有没有测量证据？ | 输出脚本、资源请求、图片和字体 |

每个准备实施的优化都先建立简短依据：具体文件或调用链、当前问题、目标职责边界、最小调整、必须保持的行为、验证方式。按正确性和影响范围排序，先修复缺陷，再处理有明确收益的封装；不必为此额外创建报告文件。

### 封装判断标准

封装的目标是降低理解成本和修改影响范围，不是单纯减少行数或增加文件数量。先问：这些代码是否表达同一规则、是否因同一个原因变化、提取后调用方是否更容易理解？

| 实际情况 | 优先处理方式 |
| --- | --- |
| 多处重复同一计算或路径规则 | 提取或复用一个输入输出清晰的函数 |
| 多处重复同一 UI 语义和行为 | 提取有明确 Props 的组件 |
| 页面区块独立且较长，已影响阅读 | 提取少量有具体职责的页面组件 |
| 字段较多且依赖数组位置理解 | 使用明确的小型对象或元组类型 |
| 同一规则存在多份来源 | 明确一个维护位置，让消费方使用它 |
| 仅外观相似，但含义或变化原因不同 | 保留独立实现，允许少量重复 |
| 只为尚未发生的复用预留接口 | 不封装 |

新增抽象应有具体名称、少量必要参数和明确边界。若出现大量布尔开关、传入整份站点数据、内部根据多种页面类型分支，或多层转发却不承担职责，应重新评估抽象是否成立。

公共函数和组件不反向依赖路由页面。路由负责选择与校验，数据模块负责提供数据，页面组件负责展示，布局负责公共骨架；这些是职责边界，不要求机械创建四层目录。

同一数据来源不意味着合并不同概念：`hasRoute()` 表示页面存在，`isIndexable()` 表示允许索引，两者应保留各自含义。不要为了 DRY 将它们压成含糊的通用判断。

### 当前项目的优先评估点

以下是需要重新核实的候选项，不是必须执行的重构清单；已经解决或收益不足的项目直接跳过。

1. 首页导入 `[...slug].astro` 的复用方式：评估是否混淆路由入口和渲染组件。若提取共享组件，应真正理顺参数与职责，不能只把大文件换个位置。
2. `[...slug].astro` 的多页面分支：按独立职责选择少量区块拆分，避免通用页面引擎和微型组件堆积。
3. `site.ts` 中的数据与工具：沿调用方判断是否难以独立维护，不仅因为文件长就拆分。调整时保持导入关系简单，避免循环依赖。
4. `channel[2]`、`channel[3]` 等位置访问：评估是否改为 `channel.description`、`channel.status` 等明确字段，并同步修改全部相关消费方。
5. 语言、路径和索引规则：检查静态路由、语言切换、导航和 sitemap 是否使用一致来源，保留各自业务无关的技术职责。
6. Props 与类型断言：优先让组件接口正确表达输入约束，防止再次出现字符串与数组不匹配或翻译命名空间错误。

## 3. 优化范围与修改尺度

本任务允许优化现有代码，包括修复 Bug、增强类型约束、减少明显重复、改善复杂模板和修正资源引用。采用完成目标所需的最小改动，不追求最少行数而牺牲完整性。

- 只修改与已确认问题直接相关的文件，不顺手重命名、全仓格式化或重新设计页面。
- 保留未涉及问题的现有实现，尊重用户尚未提交的修改，不回滚或覆盖它们。
- 不更换框架、CSS 体系、包管理器、构建工具或部署架构。
- 不新增后台、数据库、鉴权、分析 SDK、事件总线、依赖注入或插件系统。
- 不添加只是为了未来可能需求的通用配置和类型框架。
- 无关问题可在结果中简短指出，不扩大本轮修改范围。
- 常规实现细节自行选择最简单合理方案；仅在影响公开行为或重大架构选择时询问。

## 4. Astro 页面与组件

优先在构建阶段生成 HTML。不要为静态文本、导航、响应式或简单动画引入客户端 JavaScript；没有实际交互需求时不要新增 `client:*` 指令或 UI 框架。

明确区分路由参数、页面数据和组件 Props。需要对外接收属性的组件声明清晰的 `interface Props`，避免用类型断言掩盖不匹配。

`slug` 应遵循现有字符串路径约定：首页使用空字符串，详情使用 `channels/telegram` 这样的字符串。先检查真实调用方，再移除不必要的联合类型或转换，不把所有输入强制转换成字符串。

检查 `getStaticPaths()`、首页入口和详情入口是否对齐，确保有效路径正常生成，无效路径不落入错误页面分支。

当前 `[...slug].astro` 包含较多条件渲染。只有在职责混杂、重复明显或维护困难时，才按清晰的页面区块提取少量组件。路由入口继续负责路径和数据选择，共享布局继续负责页面骨架；不要创建通用页面引擎，也不要把短小标记拆成几十个组件。

避免为了复用将路由页面长期当作复杂组件接口。若确需提取共享渲染组件，要同步处理现有入口、Props 和路由数据，保证 URL 和输出不变。

## 5. TypeScript 与数据结构

- 保持严格类型，不使用 `any`、双重断言或忽略诊断来消除错误。
- 外部或不确定输入先使用 `unknown` 和类型收窄。
- 区分真实类型校验与 `as` 断言；断言不能证明数据正确。
- 检查页面键、状态、路由和翻译键之间的一致性，不通过放宽为任意字符串逃避约束。
- 多字段数组在依赖位置索引时，评估明确元组或小型对象是否更易维护。仅在收益明确时迁移，并一次更新相关使用方。
- 函数保持输入输出清晰，减少嵌套，不机械拆分小函数或引入复杂泛型。
- 只为确实可能失败的操作处理错误。缺失页面或翻译应有清晰错误，不返回成功形状的占位数据。

### 代码展开与换行

优先让代码便于阅读、定位和维护，不通过省略花括号或压缩换行来减少行数。以下规则适用于 TypeScript、JavaScript 和 Astro frontmatter：

- `if`、`else`、`for`、`while` 等控制语句始终使用花括号，即使内部只有一条 `return`、`throw` 或赋值语句。
- 条件、分支体和结束花括号按常规多行格式书写，不将整个控制语句压成一行。
- 每行只写一条独立语句，不把多个声明或操作用分号串在同一行。
- 保留提前返回和输入校验，但将它们写成带花括号的清晰代码块；不能为了减少代码删除必要校验。
- 函数包含控制流程或多步操作时使用多行函数体。短小、单一表达式的箭头函数可以保留简写，不机械展开所有表达式。
- 较长的对象、数组、调用参数和模板属性合理换行；不要为了缩短文件制造难以阅读的长行。
- 不用嵌套三元表达式、逻辑短路或逗号表达式替代本应清晰展开的控制流程。
- 对本轮新增或修改的代码应用这些规则，不为统一格式而改动无关文件，也不擅自引入格式化依赖。

不要写：

```ts
if (!isLocale(locale)) throw new Error("Invalid published locale");
```

应写为：

```ts
if (!isLocale(locale)) {
    throw new Error("Invalid published locale");
}
```

这里的“简单”指逻辑简单、职责清晰，不是代码行数最少。

## 6. 多语言代码

复用 `localeInfo`、`Locale`、`locales`、`isLocale()` 和 `t(locale, key)`，不要引入另一套语言系统。

共享 UI 和页面正文文案优先使用现有翻译资源。禁止重新大量使用 `locale === "zh-cn" ? 中文 : 英文`，也不要默认“非中文就是英文”。

检查导航、按钮、状态、表单说明及可访问性名称是否存在漏翻译。翻译键保持中英文一致，使用已有命名空间，例如 `nav.*`、`status.*`、`layout.*`。

页面元信息当前仍位于 `site.ts`。不要求为了统一而全部迁移；仅在确有重复或类型问题时做小范围整理。不要在无收益的情况下批量重命名已有翻译键。

缺失翻译继续明确报错，不悄悄回退到英文。新增语言不是本轮任务，但修改不能把现有语言注册机制退化成分散硬编码。

## 7. SEO、URL 与资源

SEO 内容直接存在于输出 HTML，不依赖客户端注入。

- 保持每页 title、description、canonical、HTML lang、Open Graph 和语义化标题正确。
- 路径复用现有工具，公开站点链接、canonical、robots 和 sitemap 使用正式 HTTPS 地址。
- `hreflang` 只指向存在的对应页面，保持语言对应和现有索引策略；不要为缺失页面伪造对应链接。
- 首页语言组的 `x-default` 指向中文首页 `/zh-cn/`，其他可索引页面指向英文对应页；不索引页面不自动新增索引信号。
- Sitemap 只收录当前已发布、可索引的 canonical URL；不要虚构 `lastmod`。
- 保留 JSON-LD 安全序列化，不能用未转义内容替代现有 `jsonLd()`。
- 检查所有图片和静态资源引用是否实际存在。当前布局引用 `/social-card.png`，必须核实文件及尺寸；缺失时修正元信息或使用已存在且合适的资源，不生成虚构素材。

不要机械替换所有 `http://`：SVG 和 Sitemap 的标准 `xmlns` 是固定标识，不是网络访问链接，必须保留。未配置 TLS 的 localhost/127.0.0.1 服务也不能仅通过替换文档协议变成 HTTPS。HTTP 状态码、方法等术语不应改成 HTTPS。

## 8. HTML、CSS、响应式与可访问性

保持语义化 HTML，页面跳转使用 `a`，交互行为使用 `button`。主页面保留一个主要 `h1`，标题层级反映内容结构。

复用原生 CSS、现有变量和布局类，不安装 Tailwind 或 UI 库。使用 flex、grid、gap 和合理的 max-width，避免不必要的绝对定位、深层选择器、额外断点和 `!important`。

检查手机、平板和桌面下的实际内容，包括英文长文本、导航、语言切换、按钮、表格、卡片和页脚。导航在断点下隐藏时，检查是否仍有可用的页面访问路径；不要未经证据新增复杂菜单交互。

保留 skip link、键盘访问、可见焦点、表单 label、合理的 alt 和必要的 ARIA。原生语义足够时不叠加 ARIA。不依赖颜色作为唯一信息。

动画优先 CSS 的 transform 和 opacity。尊重减少动态效果偏好，不能为了动画引入大型依赖。

## 9. 性能与依赖

优化以实际证据为准，不声称未经测量的性能提升。

保持少 JavaScript、少依赖和少网络请求。不为构建期的小数组处理增加缓存或状态系统。

图片设置正确尺寸，非首屏图片可延迟加载，首屏资源不要盲目 lazy load。字体保留可靠 fallback，不因样式声明就新增字体请求或多套字体文件。

不无理由升级或移除依赖。怀疑依赖未使用时，先检查源码、配置和构建；依赖整理应有明确收益，并同步更新 lock file。生成文件和 `worker-configuration.d.ts` 不作为手动清理对象。

新增依赖前说明用途、现有方案不足和为何原生实现不合适。不要为几十行逻辑安装完整框架。

## 10. 验证要求

先读取 `package.json`，只运行项目实际存在且适用于改动的命令。不要求每轮重新安装依赖；仅在依赖变化或确认缺失时安装，不删除 lock file。

当前已有：

```sh
npm run build
npm run check
```

`npm run check` 当前执行 `astro build && tsc && wrangler deploy --dry-run`。根据修改范围选择最小有效检查；需要整体验证时直接运行该命令，不重复运行它已覆盖的构建。

重要限制：普通 `tsc` 不完整检查 `.astro` 模板，Astro 构建也不等同于模板类型检查。不能因为上述命令成功就声称所有 Astro/IDE 类型错误已经消除。涉及 `.astro` Props 时，使用可用的 IDE 诊断；当前项目没有 `@astrojs/check` 依赖，若缺少必要的模板类型检查能力，明确说明限制。只有确需新增检查工具时才解释原因并按依赖规则处理。

涉及渲染、路由或 SEO 的修改，应检查生成 HTML 或响应，覆盖中英文首页、受影响页面和相关 sitemap。涉及样式或交互时，有浏览器能力则检查桌面与移动布局、键盘和控制台；没有浏览器能力时说明未做视觉验证，不能把构建成功当作视觉通过。

测试关注真实行为和回归风险，不为简单可逆的文本调整新增测试框架，也不编写只复述实现的测试。

不要运行 `deploy`、`deploy:test`、`deploy:prod` 或其他真实发布命令。dry-run 不代表已经上线。不向外部服务发送源码、凭据或用户数据。

## 11. 执行与交付

完成已授权且有依据的优化：检查项目 → 定位问题 → 设计最小方案 → 修改 → 验证 → 汇报。

按可独立验证的小批次实施，每批完成后检查调用方和输出。结构调整前记录相关行为基线，调整后比较路由、页面内容、SEO、语言对应、资源和交互；不能用“构建通过”替代行为一致性验证。

每项结构优化必须能说明“当前问题 → 职责边界 → 最小调整 → 验证结果”。验收关注调用是否更清晰、规则是否减少重复维护、类型是否更可靠、修改影响是否更集中，以及是否引入额外运行时成本。不要用拆出了多少文件、减少了多少行或增加了多少抽象层作为完成标准。

不只列建议后停止，也不为了产生修改而重构。若没有确认问题，明确说明，不制造改动。对阻塞和无法验证的部分如实说明，不隐藏失败。

最终简短输出以下信息，省略无内容的部分，不逐行解释代码：

```text
Changed:
- 修改的文件及用途

Implemented:
- 已解决的问题和实际收益；结构优化简述调整前后的职责边界

Validation:
- 实际运行的命令与结果
- 必要的验证限制

Dependencies:
- none，或实际变更及原因

Notes:
- 仅列必要的遗留问题或风险
```
