## 3. 所有权验证

不方便修改 DNS 时，使用“HTML 文件”验证：

1. 从 Google 下载专属验证文件，不更改名称和内容。
2. 将文件放入项目 `public/`，不要放到 `src/pages/` 或语言子目录。
3. 按 [生产部署文档](../deploy/production.md)发布上线。
4. 确认 Google 指定的文件地址直接返回验证内容，不是 404、登录页或首页。
5. 返回 Search Console 点击“验证”。

当前验证文件为 `public/google5afff05aaa55936c.html`，公开访问地址为：

```text
https://www.coser.eu.org/google5afff05aaa55936c.html
```

验证文件是公开的所有权标识，验证成功后继续保留，Google 可能再次检查。此方式不需要安装 Analytics 或跟踪代码管理器。

## 4. 站点地图

推荐提交总索引：

```text
https://www.coser.eu.org/sitemap.xml
```

总索引引用：

```text
https://www.coser.eu.org/sitemap-zh-cn.xml
https://www.coser.eu.org/sitemap-en.xml
```

若界面已经显示 `https://www.coser.eu.org/` 前缀，输入框只填 `sitemap.xml`。子地图可单独提交用于排查，但正常情况下不必重复提交。

站点地图只包含正式官网的已发布、可索引页面。根路径重定向、隐私与条款等当前不索引页面、测试域名和 GitHub 地址不应加入。

### “无法抓取 / 无法读取”排查

1. 确认资源和地图都使用 `https://www.coser.eu.org/`。
2. 打开条目详情，记录错误和上次读取时间，不只查看列表中的“未知”。
3. 检查总索引、子地图和 robots.txt 的状态、响应内容与跳转。
4. 若普通访问正常但 Google 仍失败，结合 Cloudflare 安全事件检查相关请求是否被挑战、拦截或限速。
5. 刚提交时可以等待重试和报告更新；持续失败则继续查具体原因，不无限等待，也不反复删除提交。

可在终端检查：

```sh
curl -i https://www.coser.eu.org/sitemap.xml
curl -i https://www.coser.eu.org/sitemap-zh-cn.xml
curl -i https://www.coser.eu.org/sitemap-en.xml
curl -i https://www.coser.eu.org/robots.txt
```

地图应返回 HTTP 200 和 XML，robots.txt 应正常访问且没有阻止官网抓取。普通请求成功不证明 Google 请求成功；仅使用 Googlebot User-Agent 也不能证明真实 Googlebot 可访问。

Sitemap 的 `http://www.sitemaps.org/schemas/sitemap/0.9` 是标准 XML 命名空间，不能替换为 HTTPS。不要为排查而关闭全站安全防护。

## 5. 网址检查与索引请求

先检查中文和英文首页，再检查重要产品页及重点渠道页：

```text
https://www.coser.eu.org/zh-cn/
https://www.coser.eu.org/en/
https://www.coser.eu.org/zh-cn/product/
https://www.coser.eu.org/en/product/
```

未收录时使用“测试实际网址”，确认网页可访问、允许索引，再按需请求编入索引。已索引页面还应关注 Google 选择的 canonical 是否符合预期；实际网址测试不能保证最终收录或证明 sitemap 抓取成功。

出现每日配额提示时停止重复提交，按提示次日再尝试。配额影响手动请求，不会关闭正常抓取，也不需要修改网站代码。Google 没有公开一个对所有资源都固定的每日额度。

## 6. 更新内容后如何处理

| 改动 | 操作 |
| --- | --- |
| 少量文案调整 | 部署后等待自动重新抓取 |
| 核心页面大幅更新 | 部署后可在配额允许时请求索引 |
| 新增页面 | 纳入 sitemap，并添加有意义的内部链接 |
| 修改或移除 URL | 更新链接和 sitemap，有等价替代时设置永久重定向；否则按情况返回 404/410 |

Google 通常会自动发现更新，但时间不固定。当前 sitemap 没有 `lastmod` 也可以工作；以后添加时应表示真实内容更新时间，不能每次构建都标记全部页面更新。

标题和描述修改后，搜索结果仍可能由 Google 根据查询重新生成。内容更新不保证排名上升。

## 7. 日常维护

| 报告 | 关注重点 | 频率 |
| --- | --- | --- |
| 站点地图 | 最终读取成功、子地图可用 | 初次设置及路由变化后 |
| 网页索引 | 重要页面的抓取错误、意外 noindex、重复或 canonical 问题 | 每周 |
| 效果 | 查询词、展示、点击及页面表现，分别观察中英文页面 | 每周 |
| 核心网页指标、HTTPS | 有数据后处理具体问题 | 定期 |
| 安全问题、人工处置 | 异常警告 | 收到通知时及时检查 |

确认账号邮件通知可用。新站无数据或样本不足时，不等于网站出错。不要追求全部页面收录：有意 noindex 的页面保持不索引；不要用“移除网址”修复未收录问题。

完成基础配置后，把精力放在真实、具体的页面内容、移动体验和内部链接上，不购买外链或批量生成低价值页面。

## 8. 第一阶段：确认抓取与索引基线（等待中）

Search Console 资源和 sitemap 是刚刚申请或提交的，当前先等待 Google 建立抓取与效果数据。本阶段暂不要求重复请求索引，也不把“没有数据”当成配置失败。以下项目等数据出现后再执行：

- [ ] 确认生产中英文页脚的“官网源码 / Website source”链接已生效。
- [ ] 在 Search Console 确认 sitemap 读取成功，并记录上次读取时间和发现的网址数量。
- [ ] 检查中英文首页、产品页、关于页和重点场景页，记录索引状态与 Google 选择的 canonical。
- [ ] 确认重要页面返回 200、没有意外 noindex，并有普通内部链接；隐私和条款草案保持不索引。
- [ ] 对未收录页记录具体原因，再决定修复或请求索引，不反复提交全部页面。

等待期间可以继续执行第 9 至 11 节的内容和品牌工作。搜索结果暂时没有页面，或“效果”报告尚无数据，都不代表网站 SEO 配置失败。之后以网址检查的索引结果为准；site: 查询仅用于辅助观察，不作为完整收录统计。

收到数据后，将状态填入第 11 节的执行记录，并按下表处理：

| 状态 | 下一步 |
| --- | --- |
| 已发现，尚未编入索引 | 检查内部链接、sitemap、服务稳定性与页面价值，观察后续抓取 |
| 已抓取，尚未编入索引 | 检查重复、空泛或缺乏独立价值的内容，完善后按需请求索引 |
| Google 选择其他规范网址 | 对照目标内容、canonical、重定向、内部链接及 sitemap，排除冲突 |
| 被 robots 阻止或存在 noindex | 确认是否有意设置，只修复不符合页面用途的限制 |
| 已索引但没有展示 | 检查用户需求与内容匹配情况，等待数据积累，不直接认定技术故障 |

## 9. 第二阶段：关键词意图与页面建设

其他网站值得研究的是品牌覆盖、用户问题、落地页和传播入口。下面是待验证的关键词方向，不是已确认搜索量或排名的词库。先结合真实客户问题与搜索结果确认意图，有 Search Console 数据后再调整。

| 意图 | 中文／英文方向 | 优先承接页面 | 本轮处理重点 |
| --- | --- | --- | --- |
| 品牌 | CoserOps、Coser Operations Center、CoserOps 官网 | 中英文首页 | 品牌、适用对象、产品方向及当前状态 |
| 产品 | 多渠道客户运营平台、multi-channel customer operations platform | 两种语言的 product 页面 | 工作流程、能力状态和限制 |
| 场景 | 线索跟进、经许可触达、客户支持、社群互动及对应英文问题 | solutions 栏目及现有详情页 | 分别说明问题、流程、前提与示例，避免重复正文 |
| 渠道 | Telegram、WhatsApp、SMS、Email 客户运营 | channels 栏目及现有详情页 | 用途、接入条件和规划状态，不宣称尚未支持的集成 |
| 信任 | CoserOps 是什么、官网源码、能力状态 | about、产品页和 GitHub README | 可验证的品牌信息与源码范围 |
| 教程 | 客户运营流程、客户信息整理、Astro 与 Cloudflare 部署 | resources 栏目及后续文章 | 当前是主题规划页，有完整正文后再新增文章路由 |

不要为尚不存在的下载、登录、注册或 APK 创建搜索入口，也不要塞入无关竞品词。Google 不使用 meta keywords 进行网页排名；关键词研究应落实到真实内容中，而非仅填标签。

### 每页完成标准

- [ ] 确定主要用户问题，自然用于 title、H1、简介和正文，不设关键词密度指标。
- [ ] 提供独立信息、真实流程、示例与限制，不只写宣传口号，不虚构客户案例；规划与演示明确标注。
- [ ] 从相关栏目链接到页面，并链接相关场景或渠道页，使用有意义的链接文字。
- [ ] 中英文事实一致；新增页面同步路由、翻译、canonical、hreflang 和 sitemap。
- [ ] 检查移动端阅读、链接和图片，部署后确认页面可访问并记录索引状态。

执行顺序：先完善首页与产品页，再选择一个最相关的场景详情页深入补充，最后发布一篇完整指南。不要一次批量生成大量薄内容页。

## 10. 第三阶段：品牌入口、分享与渠道归因

官网继续统一使用 https://www.coser.eu.org/。案例中的 CDN 地址、渠道参数和跨域 canonical 属于部署与归因设计，不能仅凭 HTML 证明它们带来了排名。当前无需为 CoserOps 新建一批渠道域名。

- [ ] 核验 GitHub 远端 About、Website、Topics 和 README。
- [ ] 选择一至两个可持续维护的社交平台，统一品牌资料，发布真实介绍并链接相关官网页面。
- [ ] 确认账号归属后再加入官网；只有代表同一组织身份的主页才考虑加入 Organization.sameAs。
- [ ] 准备有授权的品牌分享封面，配置绝对 URL 的 og:image、twitter:image 与图片说明，并确认可访问。分享预览改善不等于排名提升。
- [ ] 确有归因需求时统一参数命名，先确认统计方案能记录参数，不默认安装追踪 SDK。

渠道链接示例：https://www.coser.eu.org/en/?utm_source=linkedin&utm_medium=social&utm_campaign=brand_intro 。示例不代表已有统计能力。普通推广参数不应改变核心内容；canonical、sitemap 与内部导航继续使用不带推广参数的正式 URL。

社交链接可以帮助发现品牌，但账号数量、二维码、下载转化、停留时间或渠道参数本身不能证明 SEO 有效。第三方网站的实际流量与排名需要数据支持。平台选择见 [社交平台 SEO 与内容分发](Social-Platform-SEO.md)。

| 日期 | 页面／语言 | 改动与部署状态 | 索引状态／检查时间 | Google 选择的 canonical | 展示／点击及统计区间 | 下一步 |
| --- | --- | --- | --- | --- | --- | --- |
| 待填写 | 待填写 | 待执行或待核验 | 待检查 | 待检查 | 待有数据 | 按结果确定 |

先以页面真实可用、链接完整、索引问题有明确记录作为阶段交付，再观察相关查询展示和有效访问。无数据时记录“无数据”，不填写推测数值；Google 收录与排名没有固定完成期限。
